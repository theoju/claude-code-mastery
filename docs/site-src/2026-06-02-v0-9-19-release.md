# v0.9.19 release — CCE-78 Memory Execution scoring-honesty fix

**Released:** 2026-06-02  
**PR:** [#120](https://github.com/theoju/claude-code-self-assessment/pull/120) (version bump); substantive change landed in PR #119.

---

## What changed

v0.9.19 ships one scoring-correctness fix: the Memory Execution scorer no longer blends a cumulative all-time invocation counter into a 30-day windowed session-coverage ratio.

Before this release, `run-assessment.mjs` used `Math.max(cliBtwUseCount, btwCommandUses)` to merge `cliBtwUseCount` (a lifetime invocation count read from `~/.claude.json`) into `btwCommandUses` (a 30-day session-coverage counter). The merged value was fed into the Memory Execution numerator alongside `/clear` and `/compact` session-coverage signals. This violated the project's hard rule against mixing cumulative and windowed counter classes in the same ratio numerator:

> **(a) Time window** (windowed vs cumulative) and **(b) Counter class** (session-coverage vs raw invocation count). If the new field's class on either axis differs from existing numerator inputs, it doesn't belong in the same `sum`.*

The practical consequence: users with long account histories saw their Memory Execution ratio drift upward over time — not because their recent posture improved, but because the cumulative `/btw` count kept growing.

## What the fix does

Three targeted changes:

1. **Separate exposure.** `cliBtwUseCount` (the cumulative all-time count from `~/.claude.json`) is now surfaced as its own `signalsSummary` field — `cliBtwUseCountAllTime` — rather than blended into `btwCommandUses`.

2. **Numerator restored to windowed signals only.** The Memory Execution ratio numerator now contains only `btwCommandUses` and the `/clear` + `/compact` session-coverage counters — all 30-day windowed, all session-coverage class. The cumulative counter is no longer in the ratio.

3. **Tip-33 predicate re-routed.** The `satisfiedWhen` predicate for Boris tip 33 (`/btw` habit) was re-pointed from `btwCommandUses` (the windowed signal) to `cliBtwUseCountAllTime`. Habit-adoption checks (`>= 1`) are correctly gated against the cumulative field; windowed ratios measure recent posture.

## Why it matters

The Memory Execution score now reflects what you actually did in the last 30 days, not an accumulation of account age. A stale habit that you haven't used in months correctly shows as a gap rather than carried credit.

The root cause — mixing counter classes in a ratio numerator — is one of the two primary failure modes the project's hard rules guard against. The fix is the reference case for CCE-79 (follow-on redesign of the full Memory Execution scorer to enforce per-field semantic categorization across all four signals it originally summed). See `docs/superpowers/specs/2026-06-04-cce79-memory-scorer-redesign-design.md` for the per-field table.

## Upgrade notes

No action required. `npm run assess` after pulling this version will recompute Memory Execution with the corrected ratio; the score may decrease for users whose `cliBtwUseCount` lifetime total exceeded their recent 30-day session coverage.
