# v0.9.18 release notes

Released 2026-06-01. Bundles 13 PRs landed since v0.9.17 (2026-05-26).

## Headline changes

### All 12 Execution scorers are now real (CCE-76)

The two remaining `noTelemetry()` stubs — **Memory & Context Management** and
**Terminal & Customization** — are replaced by real transcript-derived
posture-command ratio scorers. Every dimension on the radar now returns a
measured Execution value; the italic-unmeasured label + footnote only appears
for dims whose runtime data is genuinely absent (zero qualifying sessions in the
lookback window), not because the scorer gave up.

Both scorers read the `interactive_cli ∪ unknown` session universe (CCE-71's
`interactive_or_unknown` gate) and count posture commands per session —
`/clear` + `/compact` for Memory, `/color` + `/voice` + `/focus` + `/simplify`
for Customization. Rubric targets were calibrated against the realistic per-session
ceiling of those command sets, not the old fungible-sum targets.

### POSTURE / VOLUME command partition (CCE-71)

A canonical `POSTURE_COMMANDS` / `VOLUME_COMMANDS` split in
`scripts/_usage-data.mjs` controls which session kinds feed which counters.
Posture commands are only counted from `interactive_cli` and `unknown` sessions;
volume commands (`/loop`, `/schedule`, `/babysit`, `/go`, `/batch`) are counted
across every scanned session kind because autonomous-workflow signal is real
regardless of session origin.

A `assertCommandPartition` call at module load enforces disjointness and
completeness at startup. If `npm run assess` exits non-zero with no
`assessment.json` written, check stderr for a partition assertion error before
assuming an environment problem.

### /ship Stage 2 + 3 journal counter fixes (CCE-72)

Stage 2 (verify-agent) and Stage 3 (simplify) adoption signals now use
`stageRanInEntry()`, which detects all three ship-journal format generations:
the singular `entry.stage` field, the legacy-numeric `stages_run`, and the
current-string `stages_run`. Prior to this fix, older journal entries were
invisible to the counters, undercounting verify-agent and simplify adoption.

### Canonical predicate evaluator + pre-computed next-actions (PR #106)

`scripts/predicate.mjs` is now the single source of the `satisfiedWhen` DSL.
`app/lib/assessment.ts:evaluatePredicate` is a one-line re-export — never a
copy. A CI test (`predicate-passthrough.test.ts`) asserts reference equality.

`assessment.json` now carries a `rankedNextActions` field computed at score
time: top-10 unsatisfied actions sorted by `weight × deficit`. The
`/self-assessment` skill reads from this pre-computed field instead of
re-implementing the filter and ranking logic.

### /progression milestone coverage for scheduled, remote, verification (CCE-33)

The `/progression` timeline previously had no telemetry-dated detectors for
three dimensions. Heavy real usage in `scheduled`, `remote`, or `verification`
produced no milestone, making the timeline look frozen past the first-run wall.
This release adds detectors for all three, bringing milestone coverage to all
scored dimensions.

## Upgrade notes

No breaking changes. All data formats (`assessment.json`, `assessment-history.json`,
`rubric.json`) are backward-compatible with v0.9.17. If you run `npm run assess`
immediately after upgrading, the Memory and Customization Execution scores will
change from unmeasured (`gapReason` set) to real values — expect both to start
lower than 100 and trend as your actual posture command usage is counted.

The `rankedNextActions` field is new in `assessment.json`; it is additive and
does not affect any existing consumer.
