# v0.9.18 release digest

v0.9.18 bundles 13 PRs (#99–#116) landed since v0.9.17. The headline is
closing the last two unmeasured Execution dims, fixing a scoring fidelity
regression introduced in v0.9.17, and establishing two pieces of architectural
hygiene that prevent the same class of bug from returning.

## All 12 dimensions are now Execution-scored

Memory & Context Management and Terminal & Customization were the last two
dimensions that returned `gapReason !== null` for Execution — rendered as
italic radar labels with a ¹ footnote rather than scored values. Both now have
real ratio scorers gated to the `interactive_or_unknown` session universe
(`sessionsByKind.interactive_cli + sessionsByKind.unknown`). The session-kind
gate matters: `sdk_orchestrated`, `observer`, and `subagent` sessions run with
SDK defaults and would silently dilute a posture numerator if counted in the
denominator.

Model & Effort Tuning remains the one partially-measured dim: the Opus-usage
half is scored from transcripts; effort level stays settings-only. Every other
dimension now has a denominator.

## Posture/volume command partition

A per-command `POSTURE_COMMANDS` / `VOLUME_COMMANDS` partition in
`scripts/_usage-data.mjs` replaces the earlier blanket "exclude observer/SDK
sessions" approach that v0.9.17 attempted and then reverted (it deleted
genuine autonomous-workflow signal from the scheduled dimension, dropping it
75→63).

- **Posture commands** (`/color`, `/voice`, `/focus`, `/btw`, `/clear`,
  `/compact`, `/simplify`, `/rewind`, `/fewer-permission-prompts`) are counted
  only from `interactive_cli` or `unknown` sessions. These measure what _you_
  configured; observer and SDK sessions run defaults.
- **Volume commands** (`/loop`, `/schedule`, `/babysit`, `/go`, `/batch`) are
  counted across every session kind. An autonomous-workflow signal is real
  regardless of which session emitted it.

A fail-loud `assertCommandPartition` check runs at module load and catches
disjointness violations, missing classifications, and dead classifications. If
`npm run assess` exits non-zero with no `assessment.json` written, check stderr
for this boundary error before assuming an environmental issue.

## `btwCommandUses` ratio corruption fixed

v0.9.17 introduced a subtle numerator corruption: `run-assessment.mjs` used
`Math.max(cliBtwUseCount, btwCommandUses)` to blend an all-time cumulative
invocation counter (`cliBtwUseCount`) into a 30-day session-coverage counter
(`btwCommandUses`). The blend looked ergonomic — one field for predicate
authors — but silently inflated the Memory Execution ratio's numerator for any
account whose all-time `/btw` count exceeded the 30-day window count. The fix
exposes `cliBtwUseCountAllTime` as a separate field; the tip 33 predicate routes
to that field for the adoption (`>=1`) check and leaves `btwCommandUses` as a
clean 30-day windowed counter.

The follow-on redesign for the Memory Execution scorer (per-field semantics
rather than fungible sum) is filed as CCE-79.

## /ship stage counters fixed across all journal format generations

The `stageRanInEntry()` helper in `scripts/signals.mjs` now detects Stage 2
(verify-agent) and Stage 3 (simplify) dispatch across all three ship-journal
format generations: singular `entry.stage`, legacy-numeric `stages_run`, and
new-string `stages_run`. Earlier builds undercounted those stages for journals
written before the new-string format was introduced, which produced misleadingly
low verify-agent and simplify adoption signals.

The canonical stage-number/name mapping (stages 0–7) lives inline in
`stageRanInEntry`. New stages append to the end of the workflow, never insert
in the middle, so the numeric detector arm stays stable.

## Single predicate DSL evaluator

`scripts/predicate.mjs` is now the sole source of truth for the
`satisfiedWhen` DSL. `app/lib/assessment.ts:evaluatePredicate` is a one-line
passthrough re-export — it does not contain a copy of the implementation.
`app/lib/__tests__/predicate-passthrough.test.ts` asserts reference equality;
a duplicate implementation fails CI.

When the DSL grammar evolves, edit `scripts/predicate.mjs` and the rubric
`$schema` comment. Never edit the TS file directly.

## Pre-computed `rankedNextActions` in `assessment.json`

`scripts/rank-next-actions.mjs` now writes the filtered and sorted top-10
next-actions into `assessment.json.rankedNextActions` on every `npm run assess`
run. The `/self-assessment` skill reads the pre-computed list rather than
re-implementing the `satisfiedWhen` filter or the weight×deficit ranking.
Surfacing an already-satisfied action as a TODO is a regression against this
contract — fix the data layer, not the report.

## Progression timeline: three new dimension detectors

The `/progression` timeline previously had a coverage gap: `scheduled`,
`remote`, and `verification` had no telemetry-dated detectors, so heavy real
usage in those areas produced no milestone and the timeline looked frozen past
the first-run wall.

All three now have detectors that self-date from session `start_time` over full
history (`--progression-lookback null`, independent of `--insights-lookback`).
The progression timeline uses the full session history for milestone dating, so
April milestones can appear under a 30-day scoring window — that is by design.

## Test suite

647 → 666 tests across the 39-file suite.

## No breaking changes

No schema changes to `assessment.json`, `rubric.json`, `probe-catalog.json`,
or the `satisfiedWhen` DSL. The `rankedNextActions` field is a new addition
to `assessment.json`; existing readers that don't reference it are unaffected.
