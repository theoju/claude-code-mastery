# v0.9.18 — Execution coverage complete, command partition, predicate canon

Released 2026-06-01. Bundles 13 PRs landed since v0.9.17 (2026-05-26). No
breaking changes; `npm install` pulls the new version.

## What changed

### All 12 dimensions now have Execution scorers

The last two scoring dimensions — **Memory & Context Management** and
**Terminal & Customization** — previously had no Execution scorer.
`gapReason` returned `"no telemetry"`, which meant the radar was
incomplete: the "Are you using it?" axis had two genuine gaps, not two
genuinely-unmeasured dims.

Both scorers now use transcript-backed ratio signals gated to the
`interactive_or_unknown` session universe (the union of `interactive_cli`
and `unknown`-classified sessions). This matches the precedent set by the
learning (★ Insight banner) and parallel (worktree usage) scorers —
transcript evidence is mixed into Execution only where session kind is
ambiguous-or-confirmed-interactive. The radar's italic-unmeasured labels
now apply only to dims that return `gapReason !== null` at runtime, meaning
zero qualifying sessions in the current window.

### Per-command POSTURE / VOLUME partition

A fail-loud `assertCommandPartition` check runs at module load in
`scripts/_usage-data.mjs`. It enforces that every tracked command belongs
to exactly one of two classes:

| Class | Commands | Counted from |
|-------|----------|--------------|
| `POSTURE_COMMANDS` | `/color`, `/voice`, `/focus`, `/btw`, `/clear`, `/compact`, `/simplify`, `/rewind`, `/fewer-permission-prompts` | Transcripts where `classifySessionKind` returns `interactive_cli` or `"unknown"` only |
| `VOLUME_COMMANDS` | `/loop`, `/schedule`, `/babysit`, `/go`, `/batch` | All scanned session kinds |

The rule: posture signal is real only when the user was steering the
session. Volume signal is real regardless of session origin — an autonomous
pipeline firing `/loop` is exactly the behavior you want to count.

Before this partition, observer and SDK-orchestrated sessions could silently
inflate posture-command counters, producing ratios that drifted upward over
time without reflecting any actual change in how you use the interactive
shell. The `assertCommandPartition` check catches any future drift at
startup, before `assessment.json` is written.

### /ship stage dispatch counts fixed across journal generations

The `/ship` slash command logs stage execution into journal entries. Three
journal format generations exist in the wild — singular `entry.stage`,
legacy-numeric `stages_run`, and the current string-array `stages_run`.
Stage 2 (verify-agent) and Stage 3 (simplify) dispatch counts were only
reading one format, undercounting adoption on assessments where older
journal entries were in window.

`stageRanInEntry()` in `scripts/signals.mjs` now detects all three
generations. The fix lifts the adoption signal for engineers who have
been running `/ship` since before the journal format stabilized.

### Canonical predicate evaluator

`scripts/predicate.mjs` is now the single source of truth for the
`satisfiedWhen` DSL. `app/lib/assessment.ts:evaluatePredicate` is a
one-line passthrough re-export — it contains no implementation.

A new CI test (`app/lib/__tests__/predicate-passthrough.test.ts`) asserts
reference equality between the two. If someone copies the implementation
into the TS file, the test fails. The grammar evolves in `predicate.mjs`
only; the `$schema` comment in `rubric.json` is the other artifact to
update when the DSL changes.

### Pre-computed `rankedNextActions` in `assessment.json`

The self-assessment skill used to re-implement the `satisfiedWhen` filter
and weight×deficit ranking inline. That duplication risked the skill
surfacing already-satisfied actions as TODOs (a regression that happened
and needed a data-layer fix rather than a skill fix).

`assessment.json` now includes a top-10 `rankedNextActions` array written
by `scripts/rank-next-actions.mjs` on every `npm run assess` run. The
skill reads this pre-computed list. Re-implementing the ranking in the
skill is a regression.

### /progression timeline gains three new dimension detectors

The milestone timeline previously had no telemetry-dated detectors for
`scheduled`, `remote`, and `verification`. Heavy real usage in those dims
produced no milestone entry, making the timeline appear frozen past the
first-run wall.

Three new detectors add telemetry-dated milestones for those dimensions.
The detectors follow the same pattern as the existing nine: self-dated from
session `start_time` over full history (independent of `--insights-lookback`),
which is why April dates can appear under a 30-day scoring window.

### Other fixes

- **`dismissed_gap_flags` shape**: the shape used when writing this field to
  `assessment.json` was incorrect; corrected in this release.
- **Jira workflow migration**: internal tooling migrated to the current
  Atlassian MCP integration surface. No user-visible behavior change.

## Scoring impact

If you run `npm run assess` after upgrading, expect:

- **Memory & Context** and **Terminal & Customization** Execution scores to
  appear for the first time (or change from italic-unmeasured to a real
  number) if you have qualifying interactive sessions in the lookback window.
- **Posture-command ratios** (memory, customization Execution scorers) may
  shift slightly downward if observer/SDK sessions were previously inflating
  them — this is a correction, not a regression.
- **`/ship` Stage 2/3 adoption signals** may increase if your journal has
  entries in older formats.
- **`rankedNextActions`** in `assessment.json` is now authoritative. If your
  self-assessment skill has inline ranking logic, it should be removed.

## Upgrade

```bash
git pull origin main
npm install
npm run assess:print
```

No config changes required. `assessment.config.json` and `.env.local` are
unchanged.
