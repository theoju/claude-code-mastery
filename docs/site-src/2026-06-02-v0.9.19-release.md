# v0.9.19

Version bump: `package.json` `version` moves to `0.9.19` (PR #120). The commit
itself is a one-line change — the substance of the release ships in the two
PRs it bundles under this tag.

## What's in this release

- **Memory Execution scoring-honesty fix.** Un-blends the cumulative
  `cliBtwUseCount` counter out of the windowed Memory Execution ratio's
  numerator (CCE-78). Before this fix, `run-assessment.mjs` `Math.max`'d a
  lifetime `/btw` invocation count into a 30-day session-coverage ratio,
  which silently inflated the Memory Execution score and drifted upward with
  account age rather than recent posture. The cumulative count is now
  exposed on its own summary field (`cliBtwUseCountAllTime`) instead of being
  folded into the ratio, and the corresponding rubric predicate reads from
  the cumulative field directly where a cumulative signal is actually what's
  wanted.
- **Plan archival housekeeping.** Landed plans move out of active tracking
  under `docs/superpowers/plans/` into `docs/superpowers/plans/archived/`, so
  the active-plans directory reflects in-flight work only.

## Why cut a release for this

Both changes were sitting as unreleased commits on `main`. A scoring-honesty
fix — even a narrow one scoped to a single ratio's numerator — is exactly the
kind of change that should be traceable to a tag: if you compare an
assessment run from before this release against one after, the Memory
Execution number can move without any change in your actual `/btw` usage, and
a release boundary is what makes that explainable after the fact.

## Upgrading

No config or CLI changes. Re-run `npm run assess` (or `npm run assess:print`)
after upgrading; if your prior Memory Execution score included meaningful
`/btw` usage, expect it to drop to reflect the corrected numerator — that's
the fix working as intended, not a regression. The full per-field rationale
for what belongs in a ratio numerator versus a cumulative evidence field is
tracked as a standing project rule (see CCE-78 and its CCE-79 follow-up in
this repo's project memory) and is worth reading before adding a new field to
any Execution ratio.
