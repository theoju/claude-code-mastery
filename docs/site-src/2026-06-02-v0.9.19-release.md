# v0.9.19 — Scoring honesty fix: cumulative vs. windowed /btw signal (CCE-78)

**Released:** 2026-06-02  
**PR:** [#120](https://github.com/theoju/claude-code-self-assessment/pull/120)  
**Breaking changes:** none

## What changed

v0.9.19 is a version-bump release that bundles two previously merged PRs:

- **PR #118 (CCE-78)** — unblends the cumulative all-time `/btw` invocation count from the 30-day windowed Memory Execution ratio numerator.
- **PR #119** — archives the now-landed CCE-72 and CCE-76 plans from the active `plans/` directory.

The only file touched in PR #120 itself is `package.json` (version bump to `0.9.19`).

## The scoring bug (CCE-78)

### What was wrong

`run-assessment.mjs` contained a `Math.max` blend at lines 134–137 that folded `cliBtwUseCount` (a cumulative lifetime invocation count read from `~/.claude.json`) into `btwCommandUses` (a 30-day windowed session-coverage counter from usage-data facets). The merged value was then fed into `signalsSummary.btwCommandUses` and used as part of the Memory Execution ratio numerator.

This conflated two independent axes:

| Axis | `cliBtwUseCount` | `btwCommandUses` |
|---|---|---|
| Time window | cumulative (lifetime) | windowed (30-day) |
| Counter class | raw invocation count | per-session coverage (deduped) |

For users who had adopted `/btw` at any point in their account history, the cumulative counter drifted the Memory Execution ratio upward with account age regardless of whether they had used `/btw` in the last 30 days. Scoring should reflect recent posture, not lifetime totals.

### The fix

`signalsSummary` now exposes both values separately:

- **`btwCommandUses`** — 30-day windowed session-coverage count (unchanged semantics, blend removed).
- **`cliBtwUseCountAllTime`** — the lifetime raw invocation count from `~/.claude.json`, now surfaced as a distinct additive field.

The tip 33 and tip 54 predicates, which previously tested `btwCommandUses >= 1` (and silently hit the cumulative value via the blend), are rerouted to `cliBtwUseCountAllTime >= 1`. This preserves the adoption-gate behavior — "has the user ever used `/btw`?" — while keeping the windowed ratio numerator clean.

### Impact on scores

Users whose `cliBtwUseCount` (lifetime) exceeded their actual 30-day `btwCommandUses` will see their Memory Execution score decrease to a value that accurately reflects recent usage. The tip 33 and tip 54 predicate probes are unaffected — they still fire on `>= 1` lifetime use.

## New hard rule in CLAUDE.md

CCE-78 formalizes a **per-field semantic categorization rule** for any future scorer author adding fields to a ratio numerator. Before writing the sum, classify each field on two independent axes:

| Axis | Possible classes |
|---|---|
| (a) Time window | windowed (e.g. 30-day) / cumulative (lifetime) |
| (b) Counter class | session-coverage (deduped per session) / raw invocation count |

If the new field's class on either axis differs from existing numerator inputs, it does not belong in the same sum. Route it to a separate surface: evidence text (cumulative totals), a standalone binary predicate, or a separate ratio with a matched denominator.

## What's next (CCE-79)

CCE-78 fixes the blend. The Memory Execution scorer's numerator still sums `/clear + /compact + /btw + /rewind` — four signals that aren't all the same counter class. **CCE-79** is a follow-up redesign that restricts the numerator to the two session-coverage signals (`/clear + /compact`), surfaces `/btw` as cumulative evidence text, keeps `/rewind` as a next-action probe only, and recalibrates the rubric target from 92 to 60 to match the narrowed realistic ceiling.

The CCE-72 (ship-journal stage counters) and CCE-76 (all-twelve Execution scorers) implementation plans are moved from the active `plans/` directory to `plans/archived/`. Both shipped before this release.
