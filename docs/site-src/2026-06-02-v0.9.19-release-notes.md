# v0.9.19 release notes

`package.json` bumps to `0.9.19` in PR #120. The release itself is a thin
wrapper — the version bump is the only change in that PR's diff — but it's
the cut point for two pieces of work that had already landed on `main`:
the CCE-78 `/btw` counter-semantics fix (PR #119) and a housekeeping pass
archiving landed CCE-72/CCE-76 plans (PR #118). Nothing here is
consumer-facing in the sense of changing what you run; it's a scoring-honesty
fix plus repo cleanup, bundled into a version so it's addressable.

## CCE-78: stop blending `/btw`'s cumulative count into the windowed ratio

Before this release, the Memory Execution numerator quietly mixed two
different kinds of counter together. `signalsSummary.btwCommandUses` is
supposed to be a 30-day, session-coverage number — how many sessions in the
current window show `/btw` usage. The code was `Math.max`-ing that windowed
value against `cliBtwUseCount`, a cumulative all-time invocation count
pulled from `~/.claude.json`. Because the all-time count only ever grows,
folding it into the windowed field meant the ratio drifted upward with
account age rather than reflecting recent posture — exactly the failure
mode the project's cumulative-vs-windowed counter rule exists to catch.

The fix: `cliBtwUseCount` stays cumulative, but it's now exposed on its own
field, `signalsSummary.cliBtwUseCountAllTime`, instead of being folded into
`btwCommandUses`. The `btw-side-channel` rubric predicate — the one that
checks for `/btw` habit adoption — was rerouted to read the new cumulative
field directly, since a habit-adoption check ("have you ever used this")
is exactly the case a cumulative counter is honest for. The windowed
`btwCommandUses` field goes back to reflecting only in-window session
coverage, so the Memory Execution ratio it feeds no longer inflates with
account age.

This is the same two-axis discipline the project applies to every ratio
numerator: classify each field on **time window** (windowed vs. cumulative)
and **counter class** (session-coverage vs. raw invocation count) before
summing it into anything. `/btw` and `/clear`/`/compact` don't share a
class, so they don't share a sum. The broader redesign of the Memory
Execution scorer along per-field lines — rather than a single fungible
sum — is tracked separately as CCE-79 and isn't part of this release;
this release only stops the specific cumulative-into-windowed blend.

## Housekeeping: archived CCE-72 and CCE-76 plans

PR #118 moves the completed CCE-72 and CCE-76 implementation plans into
the archived plans directory. Both tickets had already shipped (CCE-72's
ship-journal stage counters landed in PR #113; CCE-76 brought Execution
scorers to all twelve dimensions). No behavior change — just keeping
`docs/superpowers/plans/` reflecting only in-flight work.

## What to expect

If you're reading `assessment.json` or `signalsSummary` output directly:
`cliBtwUseCountAllTime` is a new field alongside `btwCommandUses`. If you
built anything against the old blended `btwCommandUses` semantics (treating
it as "has this user ever run `/btw`"), switch that check to
`cliBtwUseCountAllTime` — `btwCommandUses` is windowed-only again as of
this release.
