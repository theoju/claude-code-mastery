# v0.9.19 release notes

`package.json` bumps to `0.9.19` in this release (PR #120), but the version
bump is the smallest part of the story. This is a bundled release: it ships
one scoring-honesty fix that had been sitting on `main` since PR #119, plus a
housekeeping PR (#118) that archives completed plans. No other code changed —
if you diff the release commit against its parent, `package.json` is the only
line that moves.

## What actually shipped: the `/btw` counter fix (CCE-78)

v0.9.18 had a bug that this release formalizes the fix for: the Memory
Execution ratio's numerator was quietly corrupted by blending a **cumulative
all-time** counter into a **30-day windowed** ratio.

Specifically, `run-assessment.mjs` used to compute the `/btw` signal as:

```js
Math.max(maxProbe(s, "cliBtwUseCount"), btwCommandUses);
```

`cliBtwUseCount` comes from `~/.claude.json` and is a lifetime invocation
count — it only grows, and it grows with account age, not with recent
practice. `btwCommandUses` is the transcript-derived 30-day session-coverage
count that the Memory Execution scorer's denominator was built to match. Once
`cliBtwUseCount` exceeded the windowed count (which it always eventually
does), the `Math.max` pinned the numerator to the cumulative value, and the
ratio started drifting upward purely as a function of how long you'd been
using Claude Code — not how often you'd invoked `/btw` in the last 30 days.

The fix, landed in PR #119 and shipped here:

- `cliBtwUseCount` is no longer blended into `btwCommandUses`.
- The cumulative count is exposed separately on `signalsSummary` as
  `cliBtwUseCountAllTime`.
- The `btw-side-channel` predicate is rerouted to read from the new
  cumulative-only field instead of the windowed one.

The result: `btwCommandUses` now reflects only the transcript-scanned 30-day
window, and any predicate that genuinely wants "have you ever used `/btw`"
reads `cliBtwUseCountAllTime` explicitly instead of getting it smuggled in
through a ratio numerator.

## The rule this became

Fixing the one field wasn't the point — the point was naming the failure
class so it doesn't recur elsewhere. CLAUDE.md now carries a permanent hard
rule: **don't blend cumulative all-time counters into windowed ratio
surfaces.** Any new field going into a numerator gets checked on two
independent axes before it's added — (a) time window (windowed vs.
cumulative) and (b) counter class (session-coverage vs. raw invocation
count). If a field's class on either axis doesn't match the rest of the sum,
it doesn't go in the sum; it gets its own surface (evidence text, a separate
predicate, or a separate ratio with a matched denominator).

That per-field categorization discipline is why the Memory Execution
scorer's original design — summing `/btw + /clear + /compact + /rewind` into
one numerator — is being revisited from scratch rather than patched again.
`/btw` was cumulative-all-time, `/rewind` was a near-zero binary signal, and
`/clear` + `/compact` were the only genuinely matched session-coverage pair.
That redesign is filed separately as **CCE-79** and isn't part of this
release; v0.9.19 only ships the narrower CCE-78 fix plus the CLAUDE.md rule
that will govern CCE-79's design.
