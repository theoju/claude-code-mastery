# v0.9.19 release notes

`package.json` bumped to `0.9.19` in [PR #120](https://github.com/theoju/claude-code-self-assessment/pull/120).
The diff in that PR is just the version bump — the substance shipped in two
PRs merged just before it:

- **#119** — the `/btw` usage-count fix (CCE-78)
- **#118** — archival of the landed CCE-72 / CCE-76 plans

Patch bump, not minor: the fix below restores honesty in an internal signal
surface, it doesn't change what a typical consumer sees on the dashboard. The
full scorer redesign this fix sets up is deferred to a follow-up, CCE-79.

## What #119 fixed

`signalsSummary.btwCommandUses` is supposed to be a **30-day windowed**,
session-coverage signal — how many recent sessions show `/btw` usage. Before
this fix, it was being blended with `~/.claude.json`'s `btwUseCount`, which is
a **cumulative, all-time** invocation counter. Feeding a lifetime count into a
windowed ratio's numerator inflates it in a way that has nothing to do with
recent posture — the longer the account has existed, the higher the ratio
climbs, independent of whether you used `/btw` at all in the last 30 days.

The fix:

- `btwCommandUses` now reflects only the 30-day windowed signal.
- The cumulative value is exposed separately as `cliBtwUseCountAllTime`.
- The tip 33 / tip 54 predicates, which only need a lifetime "have you ever
  used this" adoption check, are rerouted to `cliBtwUseCountAllTime` instead
  of the blended field.

This is the concrete case behind the two hard rules CLAUDE.md now carries on
this class of bug: don't blend cumulative all-time counters into windowed
ratio surfaces, and classify every field on both axes — time window
(windowed vs. cumulative) and counter class (session-coverage vs. raw
invocation count) — before adding it to any numerator. If a new field's class
differs from what's already in the sum on either axis, it doesn't belong
there; route it to its own surface instead (evidence text, a separate
predicate, or a separate ratio with a matched denominator).

## What's still open

The Memory Execution scorer's numerator today still sums signals that were
classified with the same care only after this fix landed — restricting it to
signals that share both a time window and a counter class is a redesign, not
a patch, so it's tracked separately as **CCE-79**. This release note only
covers the specific corruption in `signalsSummary`; it doesn't claim the
Memory Execution ratio is now fully clean.

## Also in this release

`#118` archives the plans for CCE-72 and CCE-76, both of which had already
landed (posture-command coverage signals feeding the Memory & Context and
Terminal & Customization Execution scorers). No behavior change; housekeeping
only.
