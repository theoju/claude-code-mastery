# v0.9.19 — Scoring-honesty fix (CCE-78)

v0.9.19 bundles two landed PRs: a scoring-honesty fix (PR #119 / CCE-78)
that unblends two counter classes that had been silently conflated in
`signalsSummary`, and housekeeping archival of the CCE-72 and CCE-76
landed plans (PR #118).

---

## The problem

`signalsSummary.btwCommandUses` is a **30-day windowed session-coverage
counter** — it measures how many sessions in the last 30 days included a
`/btw` invocation. The scoring model's Memory Execution ratio divides that
value by the total interactive session count to produce a posture percentage.

Before this fix, `run-assessment.mjs:134` blended a second, semantically
different value into the same field:

```js
// v0.9.18 — the problematic blend
btwCommandUses: Math.max(signals.btwCommandUses, cliSignals.btwUseCount)
```

`cliSignals.btwUseCount` comes from `~/.claude.json` and is a **cumulative
all-time invocation count** — it counts every `/btw` call since the account
was created, with no time window and no per-session deduplication.

`Math.max` meant: if your historical `/btw` count was high but your recent
usage was zero, the counter projected a large 30-day value that didn't
reflect current posture. The inflated numerator drove the Memory Execution
ratio above what your actual recent sessions warranted.

The two fields differ on both axes the scoring model cares about:

| Field | Time window | Counter class |
| --- | --- | --- |
| `btwCommandUses` | 30-day windowed | per-session coverage (deduped) |
| `btwUseCount` (`~/.claude.json`) | cumulative all-time | raw invocation count |

Blending them into one `Math.max` projection violated both.

---

## What changed

**`signalsSummary` schema addition.** A new field `cliBtwUseCountAllTime`
now carries the cumulative all-time invocation count separately from the
windowed `btwCommandUses`. The existing `btwCommandUses` field is now
sourced only from the windowed scorer path — no more `Math.max` blending.

**Predicate rerouting.** The `btw-side-channel` rubric predicate (tips 33
and 54) previously evaluated against `btwCommandUses`. It has been rerouted
to `cliBtwUseCountAllTime`. Those predicates check adoption (`>= 1` lifetime
use) rather than recent posture — so the cumulative field is the right
semantic source. The predicate's behaviour for most users is unchanged; only
the field name it reads from differs.

**No Memory Execution score change.** The Memory Execution scorer already
used `btwCommandUses` as the numerator for its session-coverage ratio. The
fix corrects what `btwCommandUses` actually contains — the scorer formula
itself is untouched. If your recent `/btw` usage is genuinely low, your
Memory Execution score will reflect that more accurately now.

---

## New hard rule

PR #119 codified a new entry in CLAUDE.md under `## Hard rules`:

> **Per-field semantic categorization before adding to any numerator.** When
> adding a new field to a ratio numerator (or summing multiple fields into
> one), classify each field on two independent axes BEFORE writing the sum:
> time window (windowed vs cumulative) and counter class (session-coverage
> vs raw invocation count). If the new field's class on either axis differs
> from existing numerator inputs, it doesn't belong in the same sum.

The rule exists to make this class of mistake detectable in code review
rather than discoverable only after observing score drift.

## What's next

**CCE-79** — a deeper Memory Execution scorer redesign — was filed as a
follow-up. The current Memory Execution numerator still sums `/clear` and
`/compact` session-coverage counts alongside the (now correctly windowed)
`/btw` counter; CCE-79 will audit all numerator fields against the same
two-axis classification, recalibrate the rubric target to match the
narrowed realistic ceiling, and surface the cumulative signals as evidence
text rather than ratio inputs. CCE-79 is not merged in this release.
