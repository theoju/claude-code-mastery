- PR #101: PR #101 adds a new Conventions entry to CLAUDE.md documenting the `/progression` timeline's dual milestone-source architecture. It explains that telemetry detectors (`scripts/progression.mjs`) self-date from session `start_time` across full history, while config detectors (`scripts/config-progression.mjs`) stamp `firstSeenAt` at first-observed and freeze it. It records the deliberate first-run caveat that causes all 8 config milestones to share an identical timestamp, and documents the coverage gap where 3 of 12 scored dimensions (`scheduled`, `remote`, `verification`) have no detector — filing CCE-33 as the tracking issue.

- PR #102: Fixed a one-character schema error in `.engineering-docs-agent/state.json`: the `dismissed_gap_flags` field was bootstrapped as an empty JSON array (`[]`) but the plugin's state schema requires it to be an object (`{}`) keyed by `{owner}/{name}#{pr}`. The strict schema validation caused the orchestrator to exit with code 2 within milliseconds of startup, blocking the docs-agent nightly run entirely.
- PR #104: PR #104 addresses a recurring bug class in the /self-assessment skill where a model running the skill hand-wrote an incompatible DSL filter expecting satisfiedWhen to be an object {field, op, value} rather than the actual string format (e.g. 'loopCommandUses>=1'). The evaluator returned null for every predicate, suppressing all filtering, which caused already-satisfied actions to wrongly surface as top-3 priorities. The fix has two parts: (1) a tactical update to SKILL.md documenting the DSL grammar inline so models can evaluate correctly as a stopgap; and (2) a design spec and implementation plan for a structural solution — extracting the predicate evaluator to a Node-shareable scripts/predicate.mjs and pre-computing a ranked next-actions list in assessment.json so the skill becomes a trivial reader rather than a DSL re-implementer.
- PR #106: Introduces a canonical `satisfiedWhen` DSL evaluator (`scripts/predicate.mjs`) and a pre-computed ranked next-actions module (`scripts/rank-next-actions.mjs`). The `app/lib/assessment.ts` evaluator is reduced to a 1-line re-export of the canonical implementation. `scripts/run-assessment.mjs` now writes `rankedNextActions` into `assessment.json` so downstream consumers (the `/self-assessment` skill) read pre-ranked, already-filtered results rather than re-implementing the filter logic themselves. Tests covering predicate evaluation, ranking, and end-to-end run-assessment ranking are added. A hard rule is added to `CLAUDE.md` enforcing single-source DSL ownership.
- PR #107: Two test files updated as post-review housekeeping from PR #106: a regression test was added to pin the internal `axisOrder()` sort-order mapping (ensuring unknown axis values sort at tier 2 adjacent to 'either', not ahead of 'platform'), and a type-safety hardening test was added to the rank-next-actions suite. No production code was modified.
- PR #108: Added three new telemetry-dated milestone detectors to the `/progression` timeline — `scheduled` (Boris tip 48, triggers on first `/loop`, `/schedule`, or `/babysit` invocation), `remote` (tip 35, triggers on first `RemoteTrigger`, `PushNotification`, or `SendMessage` tool fire), and `verification` (tip 73, triggers on first `/go`). - PR #110: Codifies a posture-vs-volume command partition in the transcript-scanning layer (`scripts/_usage-data.mjs`). - PR #113: Introduced a pure helper `stageRanInEntry(entry, legacyNumber, newName)` in `scripts/signals.mjs` that normalises /ship stage detection across all three journal format generations — singular `entry.stage` (oldest), `stages_run` as an integer array (intermediate), and `stages_run` as a string array (latest). - PR #122: Post-merge documentation corrections capturing two durable operational lessons from the CCE-81 / PR #121 GitHub Pages deploy incident. CLAUDE.md received two new Conventions bullets: (1) `actions/configure-pages@v6 enablement: true` does not bootstrap GitHub Pages on a first deploy because the workflow GITHUB_TOKEN lacks admin scope, requiring a manual `gh api POST .../pages` call with a personal/admin token before the first workflow run; (2) monitor shell scripts must use bash rather than zsh because `status` and `pipestatus` are read-only built-in parameters in zsh, causing silent crashes and masking successful deploys. The same lessons were appended as recovery/post-implementation notes to the existing mkdocs-upgrade plan and design-spec docs under `docs/superpowers/`.
