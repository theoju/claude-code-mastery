- PR #104: Added a 12-line grammar block to the /self-assessment skill's SKILL.md documenting the satisfiedWhen predicate DSL string syntax (e.g. "loopCommandUses>=1"), plus a spec and plan for a broader predicate-ranker fix, to prevent models running the skill from hand-rolling an incorrect object-shaped filter that silently no-ops.
- PR #106: Introduces `scripts/predicate.mjs` as the single canonical implementation of the `satisfiedWhen` DSL evaluator (parsing string expressions like `field>=value` against signals/insights data), with `app/lib/assessment.ts`'s `evaluatePredicate` reduced to a 1-line passthrough re-export enforced by a reference-equality test. Also moves the next-actions ranking (filtering by `satisfiedWhen` + weight×deficit sort) into a pre-computed `rankedNextActions` field written to `assessment.json` by `scripts/rank-next-actions.mjs`, so downstream consumers (including the self-assessment skill) read the top-N list directly instead of re-implementing the filter/sort logic themselves.
- PR #107: Added regression tests hardening the predicate/next-action ranker's internal axis-sort behavior, closing two deferred Minor review findings from PR #106. No production code was touched — only test files under scripts/__tests__ were changed to pin the axisOrder() tie-break mapping so a future refactor that alters the platform/execution/other ordering fails loudly.
- PR #108: Adds three new telemetry-dated milestone detectors to the /progression timeline — `scheduled` (fires on first /loop, /schedule, or /babysit), `remote` (fires on first RemoteTrigger/PushNotification/SendMessage tool use), and `verification` (fires on first /go) — closing the coverage gap that previously left 4 of 12 scored dimensions without a progression milestone. Also extends `scanTranscriptModes` in `_usage-data.mjs` with a per-session `commands: Set<string>` field to support the new detectors.
- PR #110: Introduces a posture-vs-volume partition for how the scorer counts slash commands found in transcripts. Posture commands (/color, /voice, /focus, /btw, /clear, /compact, /simplify, /rewind, /fewer-permission-prompts) are now counted only when the session is classified as interactive_cli or the conservative 'unknown' fallback, while volume commands (/loop, /schedule, /babysit, /go, /batch) continue to be counted across every scanned session kind. A fail-loud assertCommandPartition check runs at module load to catch drift (disjointness, missing classification, dead classification).
- PR #111: Migrated the docs-agent-nightly GitHub Actions workflow's authentication inputs from repository secrets to repository variables: the GitHub App token step now reads `client-id` from `vars.DOCS_AGENT_APP_CLIENT_ID` instead of `app-id` from `secrets.DOCS_AGENT_APP_ID` (the latter is deprecated upstream in `actions/create-github-app-token@v3`), and `JIRA_EMAIL` is sourced from `vars.JIRA_EMAIL` instead of `secrets.JIRA_EMAIL` since it's a basic-auth username, not a credential.
- PR #113: Fixed the self-assessment scorer's `gatherShipJournal` reader so `/ship` Stage 2 (verify-agent) and Stage 3 (simplify) dispatches are credited across all three generations of the `~/.claude/ship/journal.jsonl` format (singular `entry.stage`, legacy-numeric `stages_run`, and new-string `stages_run`). Previously the reader only matched `entry.stage === 2`, silently missing roughly 41% of journal entries — the entire `stages_run` cohort — which meant users with `/ship` deeply integrated could still score `simplifyCommandUses=0`. Introduces a new pure helper, `stageRanInEntry(entry, legacyNumber, newName)`, that collapses the three detection paths into one `Array.includes` strict-equality check.

- PR #122: Recorded two durable operational lessons learned after the PR #121/CCE-81 GitHub Pages deploy incident: (1) `actions/configure-pages@v6`'s `enablement: true` does not actually bootstrap GitHub Pages on a first deploy, because the workflow's default `GITHUB_TOKEN` lacks admin scope and `permissions:` blocks can only restrict (never expand) that token's scopes — first deploy must be preceded by a manual `gh api -X POST repos/<owner>/<repo>/pages -f build_type=workflow` call (or the equivalent UI toggle) run by an admin login; and (2) monitor/poll scripts must be run under bash rather than zsh, since zsh reserves `status`/`pipestatus` as read-only built-ins and assigning to either inside a poll loop crashes the shell silently, masking otherwise-successful deploys.
