## 2026-06-04T08:35:05.674935+00:00
- PR #125: Dropped the misleading `enablement: true` parameter from `actions/configure-pages@v6` in this repo's `docs-agent-pages.yml` workflow. The field does not actually bootstrap GitHub Pages on first deploy — the default GITHUB_TOKEN lacks the admin scope required — and becomes a silent no-op once Pages already exists. The PR also records the discovery in CLAUDE.md (with the correct manual bootstrap command) and updates the mkdocs upgrade design spec with a post-implementation correction note from the v0.9.20/CCE-81 onboarding incident.
- PR #122: Post-merge documentation update following PR #121 / CCE-81 (mkdocs upgrade incident). Records three durable lessons in CLAUDE.md, the mkdocs upgrade plan, and the mkdocs upgrade design spec: (1) `actions/configure-pages@v6 enablement: true` does not bootstrap GitHub Pages on a first deploy — the workflow GITHUB_TOKEN lacks admin scope, requiring a manual `gh api POST .../pages -f build_type=workflow` call or equivalent UI step before the first CI run; (2) monitor scripts must use bash rather than zsh because `status` and `pipestatus` are read-only built-in parameters in zsh and assigning to them inside a poll loop crashes the shell silently with no event lines emitted; (3) full recovery steps for the v0.9.20 onboarding incident are now captured in the spec's post-implementation correction section.

- PR #113: PR #113 (CCE-72) introduces `stageRanInEntry()`, a format-aware helper in `scripts/signals.mjs` that detects whether a `/ship` stage ran across all three journal format generations: the oldest singular `entry.stage` integer format, the intermediate `stages_run` numeric-array format, and the latest `stages_run` string-named-array format. With this helper in place, the scorer now correctly credits Stage 2 (verify-agent) and Stage 3 (simplify) runs that arrive through `/ship`'s dispatched subagents rather than direct slash-command invocations. Previously, `gatherShipJournal` read only `entry.stage === 2`, silently missing the ~41% of entries in the `stages_run` cohort; this caused `simplifyCommandUses` and `shipVerifyStageRecent` to undercount adoption for any user who had shipped through `/ship` after the schema evolved. The PR also updates tests (`gather-ship-journal.test.mjs`, `build-signals-summary.test.mjs`), `run-assessment.mjs`, the probe implementation tracker, and adds a design spec and plan under `docs/superpowers/`.
- PR #111: Migrated the docs-agent-nightly GitHub Actions workflow to use a GitHub App client-id (via `vars.DOCS_AGENT_APP_CLIENT_ID`) for token generation and sourced `JIRA_EMAIL` from a repository variable (`vars.JIRA_EMAIL`) rather than a hardcoded value or secret. The change is two lines in `.github/workflows/docs-agent-nightly.yml`.
- PR #110: Introduces a formal posture-vs-volume command partition in the transcript scanner (_usage-data.mjs). Posture commands (/color, /voice, /focus, /btw, /clear, /compact, /simplify, /rewind, /fewer-permission-prompts) are now counted only from interactive_cli and unknown sessions, while volume commands (/loop, /schedule, /babysit, /go, /batch) are counted across all session kinds. A fail-loud assertCommandPartition guard runs at module load to enforce disjointness and catch future drift. CLAUDE.md, the probe-implementation-status tracker, and a new design spec plus plan document were updated to reflect the change.
- PR #108: Added three new telemetry-dated milestone detectors to the `/progression` timeline — one each for the `scheduled`, `remote`, and `verification` dimensions. Previously those three dimensions had no detectors in `scripts/progression.mjs`, so the progression timeline appeared frozen for users with heavy usage in those areas despite real session activity. The implementation extends `scripts/progression.mjs` and `scripts/_usage-data.mjs` and is covered by new tests in `scripts/__tests__/progression.test.mjs`. Accompanying design spec and plan docs were committed alongside the code.
