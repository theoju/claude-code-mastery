## 2026-06-01 — Docs site moved to mkdocs, published on GitHub Pages

This page is now part of a real docs site instead of a flat markdown
file rendered raw by GitHub. PR #121 upgraded the
engineering-docs-agent integration from `framework: none` to
`framework: mkdocs` and stood up
[theoju.github.io/claude-code-self-assessment](https://theoju.github.io/claude-code-self-assessment/)
— Material theme, search, and real navigation instead of a bare
`docs/*.md` tree.

What changed under the hood:

- The existing flat `docs/*.md` files were migrated verbatim into
  `docs/site-src/`, which is now the mkdocs `docs_dir`.
- `mkdocs.yml` was added at the repo root: `search` +
  `awesome-pages` + `literate-nav` (nav driven by
  `docs/site-src/SUMMARY.md`) plugins, Material theme with
  navigation tabs/sections and permalinked headings.
- `.github/workflows/docs-build-check.yml` is a new PR-level gate —
  every PR touching `docs/site-src/**`, `mkdocs.yml`, or
  `requirements-docs.txt` now runs `mkdocs build --strict`, which
  fails the build on broken internal links. Nothing broken merges.
- `.github/workflows/docs-agent-pages.yml` builds the site and
  publishes it to GitHub Pages via `actions/deploy-pages@v5` on every
  push to `main` that touches the same paths.
- `.engineering-docs-agent/config.yml` now declares
  `framework: mkdocs`, points `lens_paths.core` at
  `docs/site-src/`, and moves `whats_new_file` to
  `docs/site-src/whats-new.md` (this file) — so nightly lens fills
  and whats-new entries render through the built site going forward.

This closes out CCE-57, CCE-64, and CCE-81, and follows the standard
spec → plan → ship chain
([design](2026-06-02-mkdocs-framework-migration.md),
`docs/superpowers/plans/2026-06-01-mkdocs-upgrade.md`).

One operational wrinkle worth knowing about if you're onboarding a
new host repo the same way: `actions/configure-pages@v6`'s
`enablement: true` does **not** actually bootstrap GitHub Pages on a
first deploy, despite the name — the workflow's `GITHUB_TOKEN` lacks
the admin scope `POST /repos/.../pages` needs, so the very first run
fails with `Resource not accessible by integration` even with
`permissions: pages: write` declared. It took a one-time manual
`gh api -X POST repos/<owner>/<repo>/pages -f build_type=workflow`
run from an admin login to get this site's Pages deployment past
that first run; `enablement: true` was later deleted from the
workflow as dead weight. See the mkdocs-upgrade design doc's
post-implementation correction section for the full incident.
